# 最终项目报告：淘宝用户行为分析与购买概率预测

报告日期：2026-09-12

## 1. 项目目标

项目围绕淘宝用户行为数据，构建从原始行为记录到“用户—商品购买概率”的完整可复现流程。

最终链路覆盖：

1. 数据质量检查、清洗与 EDA；
2. 多粒度行为特征工程与关系看板；
3. 未来 1 天购买标签、时间顺序数据集划分、预处理、特征筛选和类别不平衡处理；
4. 多模型训练、Optuna 调参、Stacking 候选比较、最终测试评估和模型可解释性；
5. 固定模型与固定 Stage 3 规则的本地批量推理。

项目重点不是仅获得一个模型分数，而是保证时间口径、避免未来信息泄露、保留测试集独立性，并把结果包装成可重复执行的工程流程。

## 2. Stage 1：数据质量、清洗与 EDA

### 2.1 数据规模

原始数据质量报告记录：

| 指标 | 数值 |
| --- | ---: |
| 行为记录 | 12,256,906 |
| 用户 | 10,000 |
| 商品 | 2,876,947 |
| 类目 | 8,916 |
| 时间范围 | 2025-11-18 ~ 2025-12-18 |

五个输入字段均未发现缺失或非法值。

### 2.2 重复记录与清洗策略

质量检查发现大量同一小时、同一用户—商品—行为组合重复出现，但源时间只有小时粒度，因此项目没有简单地把所有重复记录视为错误。

最终清洗规则将：

```text
user_id + item_id + behavior_type + time
```

作为检查键，并只针对 60 次及以上的极端高频重复组保留第一条。本次正式数据中没有达到该阈值的组，因此最终清洗前后均为 12,256,906 行。

这一处理避免了在低时间粒度数据中误删真实的重复行为。

### 2.3 行为分布

| 行为 | 次数 | 占比 |
| --- | ---: | ---: |
| PV | 11,550,581 | 94.24% |
| Favorite | 242,556 | 1.98% |
| Cart | 343,564 | 2.80% |
| Buy | 120,205 | 0.98% |

浏览占绝大多数，购买仅占全部行为的 0.98%。这说明“高流量”与“购买”之间存在非常明显的数量差距。

### 2.4 用户购买行为

10,000 名用户中：

- 8,886 名至少发生过一次购买；
- 1,114 名在观察窗口内没有购买；
- 8,148 名至少出现两条购买记录。

由于数据没有订单 ID，“复购”只表示存在至少两条 buy 行为记录，不能等同于两张独立订单。

### 2.5 时间规律

- 行为最低时段：凌晨 4 点；
- 行为最高时段：21 点；
- 浏览和收藏在 21 点达到峰值；
- 加购和购买在 22 点达到峰值；
- 20–22 点是整体行为最集中的窗口。

业务含义：如果做消息触达、优惠提醒或高意向召回，可以优先测试晚间窗口，但仍需通过线上实验确认因果收益。

## 3. Stage 2：特征工程与特征关系分析

### 3.1 八类特征

Stage 2 统一构建：

1. 用户基础行为；
2. 用户活跃度；
3. 用户行为序列；
4. 商品行为；
5. 商品热度；
6. 类目行为；
7. 时间行为；
8. 转化链路。

所有特征都满足：

```text
history_end < label_date
```

并按 train / validation / test 的历史窗口独立生成，避免使用未来行为。

### 3.2 用户—商品宽表

最终 Stage 2 初版宽表：

| 指标 | 结果 |
| --- | ---: |
| 样本数 | 4,384,645 |
| 字段数 | 64 |
| 重复主键 | 0 |
| 缺失主键 | 0 |
| 异常取值 | 0 |
| 时间窗口违规 | 0 |

主键为：

```text
dataset_split + user_id + item_id
```

转化率字段的缺失均来自分母为 0，并在 Stage 3 由训练集规则统一处理。

### 3.3 Stage 2 看板观察

Stage 2 看板从特征统计结果展示了行为漏斗、行为转移、行为深度、用户活跃度、商品热度和类目流量与 BUY/PV 的关系。

在默认 train 视图中，主要描述性结果包括：

| 关系 | 观察 |
| --- | --- |
| 行为深度 | Very Low 约 2.12%，Very High 约 0.77% |
| 用户活跃度 | low 约 1.94%，medium 约 1.29%，high 约 0.80% |
| 商品热度 | Very High 约 1.59%，中低热度约 0.11%–0.39% |
| 类目流量 | Medium/High 约 1.70%–1.72%，Very High 约 0.91% |

这些都是聚合 BUY/PV 描述值，不代表因果效应。它们提示：

- 活跃/行为次数高不一定意味着单次浏览更容易购买；
- 超高流量类目可能存在“流量大但购买效率下降”；
- 商品热度与购买效率存在明显分层。

因此后续建模没有只使用单一“活跃度”或“流量”指标，而是同时保留用户、商品、类目、序列和转化链路特征。

## 4. Stage 3：标签、数据集与最终特征

### 4.1 标签定义

目标为：

> 用户—商品在固定历史窗口之后的未来 1 天是否发生购买。

总样本：

| split | 样本 | 正样本 | 正样本率 |
| --- | ---: | ---: | ---: |
| train | 2,944,576 | 895 | 0.030395% |
| validation | 1,110,131 | 886 | 0.079810% |
| test | 329,938 | 616 | 0.186702% |
| overall | 4,384,645 | 2,397 | 0.054668% |

这是一个极端类别不平衡问题。

### 4.2 时间顺序划分

项目没有随机拆分数据，而是按真实时间顺序固定窗口：

| split | 特征窗口 | 标签日 |
| --- | --- | --- |
| train | 2025-11-18 ~ 2025-12-07 | 2025-12-08 |
| validation | 2025-12-09 ~ 2025-12-14 | 2025-12-15 |
| test | 2025-12-16 ~ 2025-12-17 | 2025-12-18 |

所有样本均满足特征窗口早于标签日，检查到的窗口重叠行为为 0。

### 4.3 预处理

只使用训练集拟合：

- 数值缺失值填充；
- 数值标准化；
- 字符串类别编码。

validation/test 不重新拟合。未知类别编码为 `-1`。

`user_id`、`item_id`、`category_id` 仅作追踪字段；`label` 仅作目标字段，都不进入模型输入。

### 4.4 特征筛选

候选特征：

```text
54
```

最终：

```text
37
```

删除：

- 1 个低方差字段；
- 16 个高相关冗余字段。

未发现疑似未来信息泄露字段。

### 4.5 类别不平衡方案

项目准备了四种训练方案：

| 方案 | 样本数 | 正样本率 |
| --- | ---: | ---: |
| baseline | 2,944,576 | 0.030395% |
| SMOTE | 5,887,362 | 50% |
| undersampled | 1,790 | 50% |
| class_weight | 2,944,576 | 0.030395% |

validation/test 始终保持原始分布。

## 5. Stage 4：模型训练、选择与最终评估

### 5.1 建模范围

Stage 4 比较：

```text
4 个不平衡策略 × 4 类传统模型
```

模型族包括：

- Logistic Regression；
- Random Forest；
- XGBoost；
- LightGBM。

随后对 16 个组合进行相同预算的 Optuna 调参，并比较 Stacking。

### 5.2 验证集模型选择

Optuna 后的验证集领先方案：

```text
baseline__xgboost
AUC = 0.899130
Average Precision = 0.024073
LogLoss = 0.005194
```

Stacking Logistic Regression 的验证 AUC 为 0.896450，没有超过单模型 XGBoost。

因此最终候选保留：

```text
baseline__xgboost
```

模型选择只依赖验证集，测试集未参与调参或候选选择。

### 5.3 测试集最终结果

| candidate | Test AUC | AP | Recall@0.5 | LogLoss |
| --- | ---: | ---: | ---: | ---: |
| baseline__xgboost | **0.874953** | **0.029451** | 0.000000 | **0.011206** |
| undersampled__lightgbm | 0.864176 | 0.018270 | **0.938312** | 1.005017 |
| stacking_logistic_regression | 0.861004 | 0.012590 | 0.000000 | 0.012200 |
| undersampled__random_forest | 0.846724 | 0.009718 | 0.910714 | 0.751291 |

最终 XGBoost 在排序能力、Average Precision 和 LogLoss 上表现最好，因此作为 Stage 5 的购买概率模型。

### 5.4 为什么默认 0.5 阈值不可直接用于运营

测试集正样本率只有：

```text
0.1867%
```

在阈值 0.5 时，最终 XGBoost 不产生正类预测。

阈值敏感性分析显示，在阈值 0.05 时：

```text
precision = 0.074803
recall    = 0.061688
f1        = 0.067616
```

因此本项目真正稳定的产物是**购买概率排序**，而不是“固定 0.5 阈值分类”。

业务部署建议根据：

- 每日可触达人群；
- 优惠成本；
- 单次转化收益；
- 误触达成本；

选择 Top-K 或收益最大化阈值。

### 5.5 高召回模型的权衡

`undersampled__lightgbm` 在 0.5 阈值下测试 recall 达到 0.938312，但：

```text
precision = 0.003161
false positives = 182,264
```

说明其高召回来自极大量误报。

如果业务需要“尽可能不漏掉潜在购买者”，可把它作为候选召回器；如果需要控制营销成本，不应直接使用该输出作为最终触达名单。

## 6. 模型可解释性与错误样本

### 6.1 SHAP 重要特征

Top 信号包括：

| 特征 | Mean \|SHAP\| |
| --- | ---: |
| `last_behavior_days_ago` | 1.135047 |
| `last_10_behavior_sequence_code` | 0.523118 |
| `item_cart_count` | 0.403292 |
| `user_buy_count` | 0.384174 |
| `user_unique_category_count` | 0.292961 |
| `user_unique_item_count` | 0.259256 |
| `category_fav_count` | 0.214881 |
| `item_total_count` | 0.174674 |
| `buy_per_cart` | 0.132185 |
| `item_unique_user_count` | 0.104432 |

这说明模型主要利用：

- 行为新鲜度；
- 最近行为路径；
- 加购等强意向行为；
- 用户历史购买与探索范围；
- 商品/类目热度和转化表现。

SHAP 表示模型关联，不代表因果关系。

### 6.2 长尾问题

以 `item_total_count <= 1` 定义长尾商品：

```text
long-tail samples = 77,428
positive samples = 26
```

在解释性分析使用的 0.05 阈值下，长尾商品正样本 recall 为 0。

非长尾商品的 F1 为 0.069280，高于长尾商品。

这表明当前监督模型对历史极少的商品缺少有效信号。建议：

- 单独设计长尾/新品候选池；
- 使用内容/类目先验；
- 增加探索流量；
- 不用同一概率阈值覆盖所有商品生命周期。

冷启动用户仅 102 条且没有正样本，因此当前数据不足以对冷启动用户效果做可靠结论。

## 8. 业务洞察与运营建议

### 建议 1：以“意向信号 + 新鲜度”优先，而不是只看活跃次数

Stage 2 描述结果显示，高活跃/高行为深度人群的聚合 BUY/PV 不一定更高；Stage 4 SHAP 又显示 `last_behavior_days_ago`、最近行为序列和 `item_cart_count` 是重要信号。

因此更合理的触达优先级是：

```text
近期行为 + 加购/路径信号 + 模型概率
```

而不是简单选择“最活跃用户”。

### 建议 2：晚间 20–22 点优先做营销时段实验

EDA 显示：

- 21 点流量最高；
- 22 点加购和购买达到峰值。

可以优先把优惠提醒、购物车召回等实验放在晚间，但需要 A/B 测试验证增量效果，避免把自然高峰误认为触达因果效果。

### 建议 3：使用概率排序或 Top-K 触达

极端类别不平衡下，固定 0.5 阈值几乎没有业务可用性。

建议根据每日预算，例如：

```text
Top 1,000
Top 5,000
Top 1%
```

比较命中率、转化率和成本，再选实际名单规模。

### 建议 4：高召回模型可作为第一阶段候选召回

欠采样 LightGBM 具有非常高的 recall，但误报量巨大。

可考虑两阶段方案：

```text
高召回模型扩大候选集
        ↓
最终 XGBoost / 规则 / 成本约束进行排序和过滤
```

而不是直接用高召回模型做全量营销。

### 建议 5：长尾商品使用单独策略

当前模型在长尾商品上几乎没有有效正样本召回。

建议结合：

- 类目级统计；
- 商品内容特征；
- 新品探索；
- 更长历史；
- 冷启动推荐策略。

## 10. 限制

1. 数据观察窗口较短，时间漂移需要在更长周期验证。
2. 正样本极少，Precision/Recall 对阈值非常敏感。
3. 当前主要特征来自行为统计，不包含商品文本、图像、价格等内容特征。
4. 长尾商品和冷启动用户缺少足够监督信号。
5. `purchase_probability` 目前用于排序更合理，未进行专门的概率校准。
6. 模型二进制通过 Python 序列化交付，对 `scikit-learn` / XGBoost 版本存在兼容性要求。
7. 当前是离线批量推理，不是在线实时服务。

## 11. 最终结论

项目已经完成从 1,225 万条行为数据到用户—商品购买概率的完整工程链路。

最终 `baseline__xgboost` 在独立测试集取得：

```text
AUC = 0.874953
Average Precision = 0.029451
```

在高度不平衡场景下，它的主要价值是对 329,938 个 test 用户—商品样本进行购买倾向排序，而不是依赖默认 0.5 阈值做硬分类。

结合行为分析和模型解释，最值得运营关注的是：

- 行为新鲜度；
- 最近行为序列；
- 加购等高意向行为；
- 用户历史购买/探索行为；
- 商品与类目热度；
- 晚间高活跃窗口；
- 长尾商品单独治理。

最终项目具备代码、配置、测试、文档、轻量结果和本地批量推理入口，能够在不向 GitHub 上传大数据和模型文件的前提下复现完整流程。
